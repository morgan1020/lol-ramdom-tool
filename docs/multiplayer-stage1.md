# 多人同步房間：第一階段

這是開發分支的桌面測試功能，尚未包含在公開的 v1.4.3 安裝檔。目標是驗證多個 App 連到同一房間，由主持人抽籤，所有成員收到相同結果。

## 可以測什麼

- 建立房間、以房間代碼申請加入、主持人核准或拒絕加入。
- 正式名單可有 1～5 位玩家，待核准申請另有 4 人上限。玩家使用完整 `名稱#標籤`，待核准申請不影響抽籤。
- 正式 App 成員核准且在線時，主持人才能抽籤。主副位規則沿用單機抽籤。
- 主持人可移除成員；主持人離開即結束房間，不會自動轉移主持權。
- 斷線自動嘗試恢復原身分；名單或連線變動會封存舊結果，恢復連線後即可再抽。
- 結果有單調遞增的版本；服務端去重操作，客戶端忽略舊狀態，不自動重送未確認的抽籤。

初版僅同步結果。目前測試分支的套用與分享流程請見 [多人房間操作](multiplayer-cloud.md)。玩家名稱目前是自行填寫或從本機大廳讀取，不代表經 Riot 驗證的登入身分；主持人須確認加入者是自己的朋友。

## 本機啟動

請使用 Node.js 22.12 以上，先執行 `npm ci`。

第一個終端機：

```powershell
npm run room:server
```

第二個終端機：

```powershell
npm run desktop
```

在 App 選擇「多人房間」，服務網址填入 `ws://127.0.0.1:8787/sync`，填寫完整 Riot ID 後建立或加入房間。需要先啟動服務；一般 `npm run desktop` 不會自動啟動房間服務。

也可用雙視窗示範一次開啟隔離的兩份 App 與本機服務：

```powershell
npm run room:demo
```

示範使用合成玩家及獨立 `release/sync-room-demo/` 設定目錄，不讀取真實大廳、不寫入 LoL、不使用日常 App 的統計或 Webhook。兩個視窗可自行建立／加入同一房間，核准後抽籤。關閉示範視窗後，本機服務會結束。示範資料不納入 Git。

## 測試流程

1. 主持人建立房間，將房碼給另一個視窗。
2. 成員加入後，主持人核對完整 Riot ID，再按核准。
3. 主持人直接抽籤，確認兩邊完整名單、分路、結果版本一致。
4. 切換到抽英雄或抽分路再回房間，確認房間仍保留。
5. 加入者關閉「自動套用我的分路」，確認下一輪仍收到結果且沒有模擬寫入。
6. 測試移除、離開及主持人關房，確認所有成員看到相符狀態。

自動化局部驗證：

```powershell
npm run room:test
npm run room:ui-smoke
```

房間核心測試驗證權限及抽籤規則；transport 測試使用真實本機 WebSocket 與合成身分，驗證多客戶端、去重、重連及拒絕越權。UI 冒煙驗證使用隔離 App 資料。這些測試不等於真實多人 LCU、跨電腦或公網驗收。

## 連線與資料界線

原型服務預設只監聽 `127.0.0.1`，路徑為 `/sync`。桌面客戶端只允許本機明文 `ws`，遠端必須使用 `wss`；網址不能帶帳密、查詢參數或片段。房碼是加入入口，主持人仍需核准。

房間、成員及 session token 只存在記憶體中；token 不送進 renderer、不放入網址或設定檔。服務不接收 LCU 憑證、Webhook 或歷史統計。正常關閉 App 視窗時，會先嘗試離房，最多等候一秒；服務重啟則所有房間消失。成員斷線保留身分，主持人可移除；主持人斷線超過 60 秒後，會於下一次 30 秒清理檢查關房。閒置房間預設兩小時到期。原型設有訊息大小、請求頻率、連線數及房間數上限，但尚未作為公開網際網路服務驗收。

## 協定與模組

- `src/domain/syncRoom.js`：純房間狀態轉換，不依賴 Electron、WebSocket 或雲端平台。
- `server/syncRoomServer.js`：Node 原型服務，建立身分、核對 session、限制流量並廣播狀態。
- `src/desktop/syncRoomClient.js`：主程序連線、快照驗證、操作逾時與重連；只暴露欄位白名單的公開快照。
- `src/desktop/syncRoomIpc.js`：驗證 App 主 frame，拒絕 renderer 發送 transport 專用指令或指定操作者身分。
- `src/desktop/syncRoomLifecycle.js`：關閉視窗時有界等待離房，失敗或逾時仍能正常結束 App。

每則請求為 JSON，帶正整數 `requestId` 與 `type`。初次 `create {name}` 或 `join {roomId,name}` 成功後，服務回傳 `ack {requestId,ok,token,memberId,room}`。斷線以 `resume {token}` 恢復原身分；主程序只將公開 `room` 與連線狀態送給介面。

房間操作包括 `approve/remove {memberId}`、`ready {ready}`、`draw`、`leave`、`close`。服務從 session 取得 actor，不接受外部 `connection` 或偽造 actor。成功狀態另廣播 `state {room}`，結束則推送 `ended {message}`。

同 session 的 requestId 單調遞增，服務保留最近 128 筆操作回應供去重，已過期的舊 ID 不再執行。`revision` 用於避免舊快照覆蓋新狀態；`resultVersion` 在結果失效後仍保留並遞增。操作逾時不自動重送，需先確認目前房間狀態。

預設上限：100 間房、100 條連線、單則請求 8 KiB、每連線每秒 30 則訊息、握手 10 秒逾時；每 30 秒檢查心跳與到期。客戶端重連最多 5 次，從 500 毫秒起倍增等待。服務端拒絕帶網頁 Origin 的連線；此原型專供 native 客戶端。

## 下一階段

- 將服務端房間核心接到 Cloudflare Worker／Durable Object，驗證部署、TLS 與跨電腦連線。
- 兩台實機核對完整大廳、帳號與隊伍，才開始整合各自本機分路套用；換帳號／隊伍、開始排隊時須拒絕過期結果。
- 以結果 ID 實作持久化統計去重，以及僅主持人送出一次 Discord；不能把重新連線當成新抽籤。
- 考慮主持人偏好設定、主位衝突提示及服務可用性。第一階段採全隨機。

本階段沒有部署雲端、發布新版或執行真實 LCU 寫入。
